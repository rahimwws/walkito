# Tread — HealthKit Integration Spec

Library: `@kingstinct/react-native-healthkit`

Build a background HealthKit pipeline that reads mobility, activity and sleep
data, maintains rolling baselines, feeds the home brief, and writes Tread
sessions back into Health.

**Do not change the UI.** You are adding data, logic and strings into slots
that already exist.

---

## CRITICAL — read first

**Requesting a permission you haven't authorized, or querying before
authorization completes, crashes the app.** This is stated explicitly in the
library docs. Two rules follow:

1. Never call a data hook in the same component that is requesting
   authorization. Authorization must complete first.
2. Every read must be wrapped so that a missing or denied permission returns
   `null`, never throws.

The app must render a complete, correct home screen with **zero** HealthKit
permissions granted. Health data is an enhancement, never a dependency.

# PART 1 — SETUP

## 1.1 Install and config plugin

```json
{
  "expo": {
    "plugins": [
      ["@kingstinct/react-native-healthkit", {
        "background": true,
        "NSHealthShareUsageDescription":
          "Tread reads your steps, walking pattern and sleep so your plan starts from what you have actually been doing.",
        "NSHealthUpdateUsageDescription":
          "Tread saves your sessions to Health so they count toward your activity."
      }]
    ]
  }
}
```

`"background": true` adds the `HealthKit` background delivery entitlement.
Rebuild the dev client after adding it — a JS reload is not enough.

## 1.2 Types to request

**Read:**
```
HKQuantityTypeIdentifierWalkingAsymmetryPercentage
HKQuantityTypeIdentifierWalkingSpeed
HKQuantityTypeIdentifierWalkingStepLength
HKQuantityTypeIdentifierWalkingDoubleSupportPercentage
HKQuantityTypeIdentifierStepCount
HKQuantityTypeIdentifierDistanceWalkingRunning
HKQuantityTypeIdentifierRestingHeartRate
HKQuantityTypeIdentifierHeartRateVariabilitySDNN
HKCategoryTypeIdentifierSleepAnalysis
HKWorkoutTypeIdentifier
```

**Write:**
```
HKWorkoutTypeIdentifier
HKCategoryTypeIdentifierMindfulSession
```

## 1.3 Where to request

The existing onboarding `health-step.tsx`. Request read and write **together**
in one call — a second prompt later has much lower acceptance.

```ts
const [authStatus, requestAuthorization] = useHealthkitAuthorization(
  READ_TYPES,
  WRITE_TYPES
)
```

**Do not gate the step.** `Skip for now` must fully work.

# PART 2 — READING

## 2.1 Query pattern

Use anchored queries so each background wake reads only what is new:

```ts
const { samples, newAnchor } = await queryQuantitySamplesWithAnchor(
  'HKQuantityTypeIdentifierWalkingAsymmetryPercentage',
  { anchor: storedAnchor, limit: 500 }
)
```

Store `newAnchor` per type in local storage. Never re-read the full history
after the first backfill.

## 2.2 Initial backfill

On first successful authorization, read **90 days** for each type once.
Needed to seed baselines. Run it off the main thread with a visible
"still learning" state on the home brief.

## 2.3 Background delivery

```ts
const unsubscribe = subscribeToChanges(
  'HKQuantityTypeIdentifierStepCount',
  () => { /* refetch anchored, recompute, persist */ }
)
```

Frequency per type:

| Type | Frequency |
|---|---|
| Step count | hourly |
| Walking asymmetry | daily |
| Walking speed | daily |
| Sleep | daily |
| Resting heart rate | daily |
| Workouts | immediate |

Register subscriptions once at app start, after authorization. Tear down on
sign-out.

## 2.4 Caching — mandatory

**Never query HealthKit during a render.** The home screen reads only from
local storage. The pipeline writes to local storage in the background.

If the home brief awaits a HealthKit call, the screen stalls on cold start.

# PART 3 — DERIVED METRICS

Create `src/entities/health/model/metrics.ts`. Pure functions, unit-testable.

## 3.1 Rolling baselines

```ts
type Baseline = {
  metric: string
  mean28d: number
  stdDev28d: number
  sampleDays: number      // days with at least one sample
  lastComputed: string
}
```

Recompute **once per day**, not per read.

**Minimum viable baselines:**

| Metric | Min days | Below that |
|---|---|---|
| Walking asymmetry | 14 | show nothing |
| Step count | 7 | show nothing |
| Walking speed | 14 | show nothing |
| Sleep | 7 | show nothing |

## 3.2 Signals

```ts
type HealthSignals = {
  asymmetryToday: number | null
  asymmetryDeltaPP: number | null       // percentage points vs baseline
  asymmetryElevatedDays: number         // consecutive
  asymmetryJustNormalised: boolean
  stepsYesterday: number | null
  stepsRatio: number | null             // vs 28d mean
  walkingSpeedTrend: 'slower' | 'stable' | 'faster' | null
  sleepLastNightMin: number | null
  restingHRDelta: number | null
  dataAvailability: 'none' | 'learning' | 'ready'
}
```

## 3.3 Thresholds — set them high

| Signal | Condition |
|---|---|
| Asymmetry elevated | delta ≥ **3.0 percentage points** AND **3+ consecutive days** |
| Asymmetry normalised | was elevated, now within 1.5pp of baseline for 2 days |
| Step overload | yesterday > mean28d × **1.4** |
| Walking slower | 7-day mean < baseline − 1 stdDev |
| Poor sleep | < 6h, and baseline exists |

**A single day never triggers anything.** One walk carrying a bag on one
shoulder must not fire the gait signal. A false positive costs more trust than
a missed true positive.

## 3.4 Data availability

```
none      = 0 asymmetry samples in the last 14 days
learning  = some samples, baseline not yet valid
ready     = baseline valid
```

`none` is common and expected. Mobility metrics require the phone **in a
pocket**, on flat ground, during steady walking. Phone in a bag, in a hand, on
an armband, or a running belt produces no samples. Developers have reported
walking a full mile with the phone in a pocket and receiving zero samples.

Plan for a meaningful share of users sitting permanently in `none`.

# PART 4 — THE HOME BRIEF

Insert Health states into the existing ladder in `home-page.tsx`. First match
wins.

```
1.  pain >= 7 today                       → flare
2.  pain rose 3+ vs 7d avg                → spike
3.  asymmetryElevatedDays >= 3            → gait change      NEW
4.  retest available                      → retest
5.  stepsRatio > 1.4                      → overload
6.  sleepLastNightMin < 360               → poor sleep       NEW
7.  away 4+ days                          → return
8.  session done today                    → done
9.  asymmetryJustNormalised               → gait recovered   NEW
10. program day < 8                       → early
11. dataAvailability === 'none', day 7+   → no data          NEW
12. dataAvailability === 'learning'       → learning         NEW
13. otherwise                             → default
```

Gait sits **above** load because it is the more specific signal, and **below**
pain because the person always outranks the sensor.

## Copy

Follow the existing token structure — grey frame words, emphasised values,
red for warnings.

**gait change**
```
{name}, your steps got 🚶 uneven — 8% vs your usual 2%,
and it's the ⚠ third day.
```

**gait recovered**
```
{name}, your walk is ✅ even again. Back to 2%.
```

**overload**
```
{name}, you covered 👣 14,200 steps yesterday —
⚠ 40% above your usual. Today is 🌙 recovery.
```

**poor sleep**
```
{name}, you slept 💤 5h 20m. Tendons rebuild at night —
today is 🌙 lighter.
```

**learning**
```
{name}, I'm still learning how you walk.
Give me 📅 a few more days with your phone in your pocket.
```

**no data**
```
{name}, I can't read your walk — keep your phone in a
👖 pocket, not a bag, and I'll pick it up.
```

The last two are not decorative. Without them, an empty feature reads as a
broken app.

# PART 5 — LANGUAGE RULES, NON-NEGOTIABLE

Walking asymmetry does **not** predict injury. A secondary analysis of an RCT
with 800+ runners found asymmetry did not raise injury risk, and some forms
were associated with *lower* risk. There is no population norm to compare
against.

Therefore: **compare the person only to themselves.**

| Forbidden | Required |
|---|---|
| You're limping | Your walk changed |
| You're compensating onto your left | Your steps are less even than usual |
| This is injuring you | This often happens when something hurts |
| Your asymmetry is high | Your asymmetry is 8% vs your usual 2% |
| Normal is under 3% | *(never state a norm — none exists)* |

Never surface a Health signal alone as a conclusion. Always pair it with the
user's own pain log or load. Asymmetry by itself means nothing.

This is also an App Store matter: inferring a physical condition from an
estimated metric is diagnostic-adjacent. Apple labels Mobility metrics as
**estimated**.

# PART 6 — WRITING BACK

Highest value per hour of work in this whole spec, and zero risk.

## 6.1 Sessions as workouts

On every completed session:

```ts
await saveWorkoutSample(
  'other',
  [],                                  // no quantity samples needed
  startDate,
  { endDate, metadata: { HKWorkoutBrandName: 'Tread' } }
)
```

Result: Tread appears in the Health app next to running, contributes to the
Move ring, and shows in the weekly summary. Free visibility inside an app the
user opens without you.

## 6.2 Recovery sessions as mindful minutes

For `Recovery` days:

```ts
await saveCategorySample(
  'HKCategoryTypeIdentifierMindfulSession',
  { value: 0, start: startDate, end: endDate }
)
```

## 6.3 Rules

- Write **only** on genuine completion, never on open or skip
- Never write pain scores or retest results to Health — they are not Health
  data types and the mapping would be wrong
- Write failure is silent to the user, logged for you
- Idempotent: a session written twice must not create two workouts

# PART 7 — WATCH QUESTION IN ONBOARDING

Ask it, but frame it correctly and do not over-promise.

**What each device actually delivers through Health:**

| Device | Available |
|---|---|
| iPhone alone | asymmetry, walking speed, step length, double support, steps |
| + Apple Watch | + heart rate, HRV, sleep, workouts, running dynamics |
| + Garmin | workouts, heart rate, steps, sleep. **Running dynamics stay in Garmin Connect** |
| + Whoop | workouts, heart rate, sleep, recovery. No gait data |

**Mobility metrics come from the iPhone, not the watch.** The watch question
does not affect the gait feature at all.

Copy per answer:
- **Apple Watch** → `Everything works already.`
- **Garmin** → `Turn on Apple Health sync inside Garmin Connect.` + link
- **Whoop** → `Turn on Apple Health sync inside the Whoop app.` + link
- **Nothing** → `Your phone in your pocket is enough.`

The last one must not read as a lesser tier. Gait works without a watch, and
gait is the point.

# PART 8 — FAILURE HANDLING

Every one of these currently fails silently. All must produce a state.

| Case | Behaviour |
|---|---|
| `isHealthDataAvailable()` false (iPad, simulator) | Hide the Health step entirely, app works normally |
| Authorization denied | `Health access was declined. Your plan works without it.` |
| Authorized, zero samples | `Connected — nothing yet. It fills in as you move.` |
| Partial grant (steps yes, asymmetry no) | Every signal independently null-checks its own type |
| Background delivery fails to register | Log, fall back to foreground refresh on app open |
| Anchored query throws | Reset that type's anchor, re-backfill 30 days once, log |

**HealthKit authorization status is not readable for read permissions** — iOS
deliberately hides whether a read was granted, to prevent apps inferring health
facts from a denial. So you cannot ask "was asymmetry granted?". You can only
observe whether samples come back. Treat "no samples" and "denied" as the same
state: `none`.

# PART 9 — STORAGE

```ts
HealthCache {
  anchors: Record<string, string>
  baselines: Record<string, Baseline>
  dailyMetrics: Array<{
    date: string
    steps: number | null
    asymmetryPct: number | null
    walkingSpeed: number | null
    sleepMin: number | null
    restingHR: number | null
  }>                                    // keep 90 days, roll off older
  signals: HealthSignals                // recomputed daily
  lastBackgroundRun: string
}
```

Everything local. **Never send raw health data to a server.** The onboarding
already promises `Your health data never leaves this device.` — keep that true.
If you ever add sync, that string must change first.

# PART 10 — TESTS

1. App renders a complete home screen with zero permissions granted
2. `isHealthDataAvailable()` false → Health step hidden, no crash
3. Authorization requested once, both read and write, in one call
4. Anchored query returns only new samples on the second call
5. Baseline is not computed below the minimum sample days
6. Asymmetry delta of 3.5pp on **one** day fires nothing
7. Same delta on three consecutive days fires `gait change`
8. Delta returning within 1.5pp for two days fires `gait recovered`
9. Steps 1.45× the baseline fires `overload`
10. Session completion writes exactly one workout
11. Completing the same session twice writes one workout, not two
12. Pain 8 outranks an elevated asymmetry signal in the ladder
13. Partial permission (steps only) produces step signals and null gait signals
14. Cold start renders from cache without awaiting any HealthKit call

# BUILD ORDER

1. **Write-back** — one day, zero risk, immediate value
2. Authorization plus availability states
3. Anchored reads plus backfill plus cache
4. Baselines and signals
5. Brief states
6. Background delivery
7. Watch question copy

Ship 1 and 2 before anything else. Then instrument step 4 and **measure what
share of users reach `ready`.** If it is under 40%, the gait feature is not
worth building further — report the number before continuing.
